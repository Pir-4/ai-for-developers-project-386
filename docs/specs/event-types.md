# Specification: Event types

- **Stage**: review fixes — restore the mandatory event-type model (Hexlet review, 2026-10).
- **Branch / PR**: `feat/event-types`.
- **Superseded in part** by `single-owner.md`: there is one predefined owner (no `ownerEmail` in
  routes or models), the duration is a multiple of 30 from 30 to 240, slots start every
  30 minutes (not one meeting length apart), and guest routes are `/book` and `/book/:eventTypeId`.

## 1. Goal

The owner defines **event types** — kinds of bookable meetings with a name, a description and a
duration. A guest first picks an event type, then a date, then a free slot of that type's length.
The owner's availability calendar (intervals of UTC instants, ADR 0001) stays as it is; event
types sit on top of it.

## 2. Model

- **Event type** — `id`, `ownerEmail`, `name` (1–100), `description` (1–500), `durationMinutes`
  (a multiple of 15, 15–240). Belongs to one owner.
- **Slot** — one rung of the slot ladder built for an event type: cells of the type's duration
  laid end to end from the start of each availability interval (unchanged algorithm,
  `server/src/services/slot-ladder.ts`).
- **Booking** — references its event type (`eventTypeId`) and snapshots its `durationMinutes`.
  A booking occupies its interval exclusively across **all** of the owner's bookings, whatever
  their event types: a 30-minute booking at 10:00 makes the 10:00 cell of a 45-minute type busy.

## 3. API (TypeSpec `contract/main.tsp`)

| Operation | Route | Responses |
|---|---|---|
| `createEventType` | `POST /owners/{ownerEmail}/event-types` | 201 EventType, 422 |
| `listEventTypes` | `GET /owners/{ownerEmail}/event-types` | 200 EventType[] (oldest first) |
| `getEventType` | `GET /owners/{ownerEmail}/event-types/{eventTypeId}` | 200, 404 |
| `listSlots` | `GET /owners/{ownerEmail}/event-types/{eventTypeId}/slots` | 200 Slot[], 404 |
| `createBooking` | `POST /owners/{ownerEmail}/event-types/{eventTypeId}/bookings` | 201, 422, 404, 409 |

`createBooking` body: `{ guestName, guestEmail, start }` — the duration comes from the event type.
`Meeting` carries `eventTypeId` and `eventTypeName`. The guest-chosen `duration` query parameter
and the `MeetingDuration` enum are removed.

## 4. Frontend

- The frontend talks to the API only through the client SDK generated by `@hey-api/openapi-ts`
  from `contract/openapi.yaml` (`web/src/generated/api/`, `make generate`). No hand-written `fetch`.
- `/book/:email` — the owner's event-type catalog: one card per type (name, description,
  duration) leading to the type's page. An owner without types shows an empty state.
- `/book/:email/:eventTypeId` — the type's name and description, a 14-day calendar, the slot
  ladder for the selected day (busy cells greyed out), and the booking form.
- `/owner/:email` — a new "Event types" section: a creation form (name, description, duration
  from 15/30/45/60/90/120) and the list of types, each with its own guest link. The meetings
  list shows each meeting's event-type name.

## 5. Acceptance

1. An owner creates an event type; invalid name/description/duration → 422.
2. A guest sees only that owner's types; an unknown type → 404.
3. Slots of a type have exactly the type's duration.
4. **Cross-type conflict**: with a 30-minute and a 45-minute type over 10:00–12:00, booking the
   30-minute type at 10:00 makes the 45-minute 10:00 slot busy, and booking it returns 409 (and
   vice versa); 10:45 of the 45-minute type stays bookable.
5. **Browser scenario** (Playwright, `make test-e2e`): owner logs in → creates a type → opens
   availability → guest picks the type, a date and a slot → books → the owner sees the meeting
   with the type's name.
